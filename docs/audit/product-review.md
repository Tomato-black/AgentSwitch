## 1. 产品定位与用户

### 1.1 一句话定位

**面向本地 AI Agent（Claude Code / Codex / Claude Desktop）的模型 API 网关：Agent 永远只指向 `127.0.0.1:<port>`，上游供应商、密钥与协议差异都在网关内统一处理，并按「逻辑模型」的有序目标链做故障转移。**

证据：`README.md:7` 的产品介绍、`README.md:9-13` 的拓扑图、`ARCHITECTURE.md:3-20` 的两平面分离。

### 1.2 目标用户

- **【事实】** 中文语境的个人开发者/小团队：UI、README、spec 全中文；内置 20 条预置中 14 条按量 + 6 条国内 Coding Plan 订阅（`internal/presets/default.json`）。
- **【事实】** 同时使用多个 Agent 的用户：接入页同时管理 Claude Code、Codex（CLI/桌面版/IDE 插件共用配置）、Claude Desktop。
- **【推测】** 手上有多家供应商或订阅、希望「配置一次、上游随时换」的用户；以及被上游 429/5xx 打断、需要自动切换的开发者。
- **【假设】** 是否要覆盖「完全不懂 API 配置」的新手，现有产品未做端到端向导，默认更偏向懂 `base_url`、API Key、模型名的开发者。

### 1.3 核心场景

1. **首次接入**：建渠道 → 建逻辑模型 → 为 Agent 建接入配置并应用 → Agent 重启后发起请求。
2. **日常运维**：上游故障时自动切换；换 Key、换 Base URL、调目标顺序；查看网关状态与冷却/切换情况。
3. **多 Agent / 多配置**：同一台机器上为不同 Agent、不同项目维护多套接入配置，互不干扰。
4. **第三方系统接入**：Kun 等未做自动写入的系统，按「连接指南」手工填写。

### 1.4 非目标（来自 spec，非本次新增）

- 不做 MCP / Skills / Prompts 集中管理、会话阅读、用量/配额统计页（`2026-10-17-logical-models-ccswitch-ui-design.md` §2）。
- 不做 cc-switch 的 Direct/Routing/Aggregation 三模式；一切流量走网关。
- 不做 Web 前端（2026-10-17 UI 决策）。
- 不做每渠道多 Key、全局共享 Key（渠道为单 Key 执行单元，`ARCHITECTURE.md:49`）。
- 不绕过网关直连上游（`2026-10-18-agent-access-config-design.md` 非目标）。

### 1.5 现有 UI 是否传达了定位

| 维度 | 判断 | 证据 |
|---|---|---|
| 四个一级入口（逻辑模型/渠道/接入/设置）与领域模型一致 | 清晰 | `internal/desktop/shell.go:19-27`、`internal/desktop/pages/logical/logical_view.go:20-44` |
| 「网关」这一核心差异对用户可见 | 部分可见 | 侧栏底条持续显示状态与地址（`shell.go:71-106`）；但没有任何页面解释「为什么需要网关」「与 cc-switch 的区别」 |
| 故障转移这一核心价值可感知 | 弱 | 逻辑模型编辑页只有一句「按序故障转移：靠前的目标优先」（`logical_view.go:151`）；运行期冷却与决策原因不可见（见 P1-4） |
| 首次上手有路径引导 | 弱 | 默认页逻辑模型空态引导去渠道（`logical_view.go:33-44`），但没有跨页向导或完成度提示 |

结论：**定位在 README 中非常清晰，在应用内只传达了一半**。用户能看懂「渠道、逻辑模型、接入」，但不易感知「网关在替我做了什么」，尤其在上游故障时。

## 3. 核心用户流程走查

### 3.1 首次上手：安装 → 建渠道 → 建逻辑模型 → 接入 Agent → 发起请求

| 步骤 | 用户动作 | 交互成本 | 困惑点/风险 |
|---|---|---|---|
| 1 | 启动应用 | 0 次点击 | 网关自动启动；无渠道/模型时底条显示「降级 · 没有可用的逻辑模型或渠道」（`desktop.go:154-160`、`uikit/theme.go:150-157`）。新用户可能误以为安装失败。 |
| 2 | 进入渠道页 | 1 次（侧栏） | 默认页是逻辑模型；空态有「去添加渠道」按钮（`logical_view.go:33-44`），路径可达。 |
| 3 | 添加渠道 | 1 次 | 20 条预设无搜索（`channels_new.go:29-34`），需要逐格找供应商。 |
| 4 | 选预设、填 Key | 2–3 次 + 输入 | 预设自动回填 Base URL/名称/建议模型；用户只需填 Key，体验较好。 |
| 5 | 创建渠道 | 1 次 | 创建后直接进详情页（`channels_form.go:190-205`），没有成功提示；建议模型随创建落库，用户不点保存也不会丢。 |
| 6 | 进入逻辑模型页 | 1 次 | 侧栏切页会丢弃未保存的渠道编辑（本例已创建，无影响）。 |
| 7 | 新建逻辑模型、填名、加目标、选渠道/模型、保存 | 6–8 次 | 模型下拉数据源是渠道建议模型，首次配置若没填建议模型则退化为手输（`logical_view.go:198-206`）。 |
| 8 | 进入接入页、选 Agent、新建配置 | 3 次 | 没有启用逻辑模型时仍可点「新建配置」，保存时才报错（见 P2-8）。 |
| 9 | **保存接入配置** | 1 次 | 只落库，不写 Agent 文件；成功文案是「已保存」（`accesskit/editor.go:181-182`）。 |
| 10 | **点「应用」** | 1 次 | 这是真正写 Agent 配置的动作；列表上方有「当前没有配置被应用」提示（`access.go:173-175`），但保存成功文案没有告诉用户下一步。**首次上手最可能断在这一步**（见 P1-2）。 |
| 11 | 重启 Agent / 新建对话 | 外部动作 | Codex 桌面版需完全退出再打开（`access.go:151-154`）；Claude Code 下次启动生效。 |

**总交互成本**：约 16–19 次点击/输入，跨 4 个页面。**冗余点**：渠道创建后进详情、再返回列表、再切页；逻辑模型保存后回列表；接入保存后要再点应用。整体没有端到端向导，但空态文案基本能串起路径（`logical_view.go:37`、`channels_list.go:34`、`access.go:160`）。

### 3.2 日常运维：上游故障 / 换渠道 / 改密钥 / 看状态

| 场景 | 当前路径 | 成本 | 问题 |
|---|---|---|---|
| 上游 429/5xx 自动切换 | 网关自动处理 | 0 | 用户只能通过设置页「最近请求」看到「切换 N」，看不到切了谁、为什么切、冷却到几点（见 P1-4）。 |
| 换 Key / 改 Base URL | 渠道 → 卡片 → 详情 → 改 → 保存 | 3–4 次 + 输入 | 即时生效、无需重启 Agent，流程顺畅。**但**改完未保存就点「测试连通/拉取模型」会测旧值（见 P1-3）。 |
| 调目标顺序 | 逻辑模型 → 编辑 → 上移/下移 → 保存 | 2–3 次 | 无「当前命中」提示，无法确认调序是否符合预期。 |
| 停用某逻辑模型 | 逻辑模型列表 → 停用 | 1 次 | 停用被接入配置引用的模型时无任何警告（见 P2-2）；已应用的 Agent 会立刻开始报错。 |
| 改名逻辑模型 | 逻辑模型 → 编辑 → 改名 → 保存 | 2–3 次 | **已应用的 Agent 配置文件不会刷新**，Agent 仍请求旧名 → 网关 404，且 UI 无提示（见 P0-2）。 |
| 看网关是否正常 | 侧栏底条 | 0 | 状态真实性良好（`shell.go:74`）。 |
| 看最近请求 | 设置 → 网关诊断（最多 8 条） | 2 次 | 信息量少，无详情、无打开日志按钮、无导出（见 P2-7）。 |

### 3.3 接入多 Agent / 多配置管理

| 场景 | 当前路径 | 体验 |
|---|---|---|
| 为第二个 Agent 配置 | 接入页 → 切页签 → 新建 → 保存 → 应用 | 页签切换有未保存确认（`access.go:398-443`），比逻辑模型/渠道页严谨。 |
| 同一 Agent 多份配置 | 新建多份；行内「应用」切换「使用中」 | 语义清晰；非使用中配置可通过「复制启动命令/打开终端」使用（`access.go:333-358`）。 |
| 全局配置 | 每 Agent 一份 env 键值表 | 保存后自动刷新所有派生文件（`access_configs.go:218-235`），比文案预期更强；但成功/失败样式相同（见 P2-6）。 |
| 回滚 | 「还原最近备份」 | 确认框说明了覆盖范围与可再次还原（`access.go:448-462`），可用。 |
| Claude Desktop | 无全局配置，四角色映射 | 推理强度/子代理等概念不存在，UI 做了裁剪，合理。 |
| 第三方（Kun 等） | 接入 → 连接指南 → 手工复制 | 能完成手工接入，但没有任何自动写入（与 Kun spec 冲突，见 P1-6）。 |

## 4. 问题清单

> 分级口径：P0 = 破坏核心流程或造成用户可见的严重故障/卡死；P1 = 显著影响首次上手或日常运维，需要尽快修；P2 = 体验与一致性问题；暂缓 = 收益不明确或超出当前版本范围。

### 4.1 P0

## 6. 优先级建议

### 6.1 最值得优先做的三件事

1. **修复「配置状态真相」闭环（P0-2 + P1-1）**：逻辑模型改名/删除必须让已应用配置的 live 文件同步刷新或明确标记过期；接入配置保存后必须明确告诉用户「还需要应用」，最好提供「保存并应用」。这是产品核心承诺「配置一次、即时生效」的信任基础。
2. **消除 UI 冻结（P0-1）**：拉取模型、测试连通、Codex 目录生成/应用全部移出主线程，提供进行中与取消；缓存 Codex 模板。否则用户会把「应用卡死」当成产品质量问题，并可能强杀进程。
3. **把运维可见性做成最小可用形态（P1-3）**：先在渠道卡/逻辑模型卡上展示冷却与最近命中，再给最近请求加展开详情（尝试链、跳过原因、错误分类）。这直接兑现 README 的「冷却与可解释路由」，也是与 cc-switch 差异化最强的地方。

### 6.2 建议顺序

1. 文档裁决（Kun、2026-10-20 全局配置/开关、README/ARCHITECTURE 两处过期）——不涉及业务代码，先统一口径。
2. P0-1、P0-2、P1-1、P1-2——核心闭环与稳定性。
3. P1-3、P1-4、P1-5——运维可见性、托盘/二启、Kun 决策落地。
4. P2-1 至 P2-6——一致性与反馈质量。
5. P2-7 至 P2-11——诊断、文档、首启引导与体验打磨。
6. 暂缓项按真实反馈再评估。

## 7. 待确认问题（需要产品或用户拍板）

1. **Kun**：是否在近期实现 `2026-10-28-kun-access-design.md`？还是正式接受「连接指南人工填写」并删除/标注该 spec？这是文档与路线图问题，必须先定。
2. **2026-10-20 spec 的效力**：全局配置卡是保留（现状）还是删除（spec）？五个快捷开关与「从当前 settings.json 导入」是否仍要做？目前三份文档（10-18、10-19、10-20）口径不完全一致。
3. **逻辑模型改名/删除的期望语义**：自动刷新 live 文件（用户无感）还是要求显式「重新应用」（更安全）？删除时是否允许保留失效引用？这决定 P0-2 的修法。
4. **「保存」与「应用」是否合并**：是否接受「保存并应用」作为主按钮，还是刻意保留两步以降低误写 Agent 配置的风险？
5. **托盘不可用时的策略**：关窗应退出，还是保持后台但提供其他唤回方式？是否注册 `OnSecondInstance` 作为通用唤回？
6. **是否需要独立的「运行状态」页**：还是把冷却/最近请求放进现有渠道页与设置页即可？这影响 IA 与后续 UI 重构范围。
7. **Codex 元数据编辑位置**：确认长期放在接入页 per-config（现状），还是回到逻辑模型页（2026-10-27 spec）？需要同步更新 spec/README。
8. **目标平台优先级**：Linux 托盘兼容与 Windows 实机验证是否在近期版本必须解决？这影响 P1-4 的优先级。

## 8. 结论摘要

- 产品定位清晰，领域模型（渠道、逻辑模型、接入配置）在代码与 UI 中一致，首次上手路径存在但跨度较大。
- 当前最大的产品风险不在「功能少」，而在**关键状态不透明**：改名/删除导致的配置失联、保存与应用的断点、冷却与路由决策不可见、长操作冻结 UI。
- 文档层面存在多处漂移，其中 Kun spec 与实现是「有无该功能」级别的冲突，需要优先裁决。
- 建议先修状态真相与 UI 冻结，再做运维可见性；随后统一文档口径并补齐首启引导。不建议在未确认真实需求前扩展搜索、批量、向导或更多 Agent。
