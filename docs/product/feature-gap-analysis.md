# AgentSwitch 功能缺口与体验问题分析（2026-10-29）

> 输入：主 Agent 代码核实、`ui` 子 Agent 的页面/流程审查、`pm` 子 Agent 的竞品与能力矩阵（`competitive-analysis.md`、`capability-matrix.md`）。
> 本文只做分析，不改业务代码。所有「现有缺陷」结论尽量指向 `file:line`；未实机走查的视觉/键盘/DPI 结论标注「需实机确认」。
>
> 分类：
> - **A 核心功能缺失**：影响产品最主要的使用场景。
> - **B 关键体验缺失**：功能基本存在，但操作成本高、反馈不足或容易出错。
> - **C 竞争力增强**：可形成差异化，但并非当前使用必需。
> - **D 长期探索 / 不做**：成本高、价值不确定或与定位冲突。
>
> 处理方式：
> - **修交互**：不新增产品能力，只改现有交互/文案/状态。
> - **补状态**：现有能力存在，但缺少加载/空/错误/部分失败/待应用等状态。
> - **加功能**：需要新增数据、接口、页面或架构能力。

---

## 0. 结论摘要

1. **最危险的问题不是「缺功能」，而是「状态显示成正常」**：对已应用配置点「仅保存」会直接改 Agent live 文件且不备份；派生刷新失败只记日志；绑定的模型被停用/删除后接入行仍显示「使用中」。这些会让用户以为配置已生效/已备份，实际没有。
2. **AgentSwitch 的核心差异化是「逻辑模型级故障转移」，但故障转移目前不可解释**：只有 20 条内存请求 + 尝试链，重启清零，无筛选/导出；用户无法回答「刚才为什么切、切到哪、冷却到几点」。
3. **首次上手路径是通的，但每一步的「下一步」靠用户自己推断**：默认落在逻辑模型页（依赖顺序是渠道在前）、空态文案不随数据变化、保存/应用语义不清、没有「发一条测试请求」的闭环。
4. **规模化能力缺失**：渠道/逻辑模型/接入配置/20 条预置均无搜索/筛选/排序；超过 8–20 条后效率明显下降。
5. **竞品普遍具备、AgentSwitch 明确缺失的**：持久化请求/路由历史、用量/成本/配额、配置导出/导入/备份列表、搜索/筛选、通知/告警、多账号/密钥池。
6. **不建议把所有缺口都变成功能**：保存/应用/备份语义、状态重绘、错误文案、空态跳转、级联文案等应优先通过修交互/补状态解决；只有当数据/能力确实不存在时才加功能。

## 1. A 类：核心功能缺失

### A0（最高优先级）：配置写入一致性 / 保存-应用-备份语义（现有缺陷）

| 项 | 内容 |
|---|---|
| 用户问题 | 用户点「仅保存」以为只落库；实际对当前已应用配置会直接改写 Agent live 文件，且不备份。之后点「还原最近备份」无法撤销这次保存。 |
| 证据 | `internal/bridge/access_configs.go:101-128`（Update→`RegenerateDerived`）、`:258-300`（对 current 执行 `writeClaudeLive`/`writeCodexLive`，不调用 `backupLive`）；`internal/bridge/access_live.go:173-260`（备份只在 `Apply`/`RestoreLatestBackup` 调用）；`internal/desktop/accesskit/editor.go:85-96,163-223`（「仅保存」入口）。UI 子 Agent 用临时测试实测：仅保存后 live 出现新键、备份数不变；保存并应用后最新备份包含新值。 |
| 用户影响 | 「仅保存」名不副实；「写前备份」承诺在这条路径不成立；用户不敢试错，核心信任受损。 |
| 竞品对照 | CC Switch 首写前备份 + 每日备份；9Router 自动备份；LiteLLM/new-api 以 DB/部署备份为主。备份安全是竞品共同底线。 |
| 类型 | 现有缺陷 |
| 建议处理 | 修交互 + 补状态：保存只落库；只有「应用」才投影 live；任何 live 写入前先备份；列表显示「待应用/未生效」；备份覆盖「保存前」状态。 |
| 优先级 | **P0** |
| 验收 | 编辑 current → 仅保存 → live 字节不变；保存并应用 → 最新备份内容等于保存前 live；列表出现「有未应用的修改」；自动化测试覆盖两条路径。 |

### A1：请求/路由历史持久化与故障解释（P0）

| 项 | 内容 |
|---|---|
| 用户问题 | 上游 429/5xx 后自动切换，用户不知道试了哪些目标、为什么跳过、冷却到几点、哪个上游慢；重启后记录清零。 |
| 证据 | `internal/telemetry/ring.go`（100 条内存环，`RequestRecord`/`AttemptRecord` 已有渠道、模型、结果、原因、耗时）；`internal/desktop/pages/settings/settings.go:129-169`（UI 仅 20 条，可展开尝试链）；无 SQLite 历史表。 |
| 用户影响 | 故障转移是核心卖点；不可解释就无法建立信任，排障只能翻日志。 |
| 竞品对照 | CC Switch 请求日志/用量；CCR 请求/响应详情、trace、token/cost；LiteLLM 日志/回调；new-api 日志/playground；9Router 请求/翻译日志。 |
| 类型 | 新能力（数据 + UI） |
| 建议处理 | 加功能：新增 SQLite 历史表/迁移；持久化脱敏元数据（不存 prompt/response 正文）；设置页或独立子页支持按状态/模型/渠道/时间筛选、展开尝试链、导出诊断包；默认保留 7 天（2026-10-29 用户决定；暂不提供配置）。 |
| 优先级 | **P0** |
| 依赖 | `internal/telemetry`、`internal/gateway`、`internal/storage`、`internal/bridge`、设置页 |
| 验收 | 重启后历史仍在；模拟 429 可在应用内 30 秒内定位原因；筛选/导出可用；不存正文；`-race` 通过。 |

### A2：端到端接入验证 / 测试请求（P0）

| 项 | 内容 |
|---|---|
| 用户问题 | 用户配置完渠道/逻辑模型/接入后，不知道整条链是否真的通；只能打开 Agent 发真实请求，失败后再回头排查。 |
| 证据 | 渠道详情有「测试连通」`internal/bridge/channels.go:174-195`，但只测渠道，不测逻辑模型/目标链/接入；逻辑模型页无测试入口（`pages/logical/logical_view.go`）。 |
| 用户影响 | 首次上手断在「保存/应用」；失败时无法区分是 Key、模型名、协议、冷却还是接入文件问题。 |
| 竞品对照 | CC Switch 连通性检查（只测可达性）；CCR 协议探测/连通性/模型发现；new-api Playground；LiteLLM health/router。 |
| 类型 | 新能力（复用现有 provider 探测） |
| 建议处理 | 加功能：逻辑模型行/编辑页「测试模型」——按目标链依次发一条最小请求（`max_tokens` 很小），显示每个目标的成功/失败、耗时、错误类、命中目标；明确提示可能产生少量费用；测试不污染生产冷却/统计（或单独标记）。 |
| 优先级 | **P0** |
| 验收 | 选择逻辑模型发测试请求，显示状态/耗时/命中目标；失败显示下一步；不泄露密钥；有费用提示；Fake Provider 测试覆盖成功/401/429/404/全冷却。 |

### A3：用量 / 成本 / 配额可见性（P1）

| 项 | 内容 |
|---|---|
| 用户问题 | 不知道本周/本月用了多少 token、哪个渠道消耗最多、订阅额度大概还剩多少；切换目标后成本变化不可见。 |
| 证据 | `RequestRecord` 无 token/cost 字段（`internal/telemetry/ring.go:17-30`）；协议层已解析 usage（`internal/protocol/openai_stream.go:192-193`、`responses_stream.go:169-170`、`openai_response.go:45-47`），但网关未记录；无 usage 表/价格表。 |
| 用户影响 | 订阅额度用户（Coding Plan）无法规划；按量用户不知道钱花在哪；故障转移的「成本代价」不可见。 |
| 竞品对照 | CC Switch usage/heatmap/custom pricing；CCR token/cost/latency；9Router 配额窗口/成本估算；LiteLLM spend tracking；new-api usage logs。 |
| 类型 | 新能力（数据 + UI） |
| 建议处理 | 加功能：先做 token/请求/按渠道/模型/日聚合；成本用可编辑价格表 + 估算，明确不是账单；配额探测放 P2。 |
| 优先级 | **P1**（战略上调；依赖 A1 的历史基础设施） |
| 验收 | 非流式/流式均提取 token；按渠道/模型/日聚合；与 3 家供应商控制台对照 token 误差 <5%；成本标注「估算」；可关闭/清理。 |

### A4：配置导出 / 导入 / 迁移（P1）

| 项 | 内容 |
|---|---|
| 用户问题 | 换机、重装、备份、分享配置时没有出口；用户不敢把生产配置交给一个无法带走的工具。 |
| 证据 | 仓库无导入/导出实现；`access_configs`/`channels`/`logical_models` 只在本地 SQLite；备份只针对 Agent live 文件（`access_live.go`），不含应用配置本身。 |
| 用户影响 | 配置锁定；迁移成本高；无法从 cc-switch 等工具迁移。 |
| 竞品对照 | CC Switch 导入导出 + Deep Link + 云同步；CCR 本地登录/配置导入；9Router 云同步；LiteLLM config/DB；new-api DB/config。 |
| 类型 | 新能力（格式 + 安全 + UI） |
| 建议处理 | 加功能：版本化导出格式；默认不含明文密钥；可选密码加密导出（scrypt/Argon2 + AES-GCM）；导入前预览差异/冲突；支持渠道/逻辑模型/接入配置/设置；不做云同步。 |
| 优先级 | **P1**（PM 建议 P0；主 Agent 评估后放在 P1，理由见 `decisions.md` PD-5） |
| 验收 | 导出/导入 A→B 后 Claude Code/Codex 各发一条请求成功；导出文件无明文密钥（自动化扫描）；导入可回滚；冲突有预览。 |

### A5：备份历史列表 / 选择恢复（P1，与 A0 同批）

| 项 | 内容 |
|---|---|
| 用户问题 | 只能「还原最近一份」；不知道备份时间、是否有备份、备份内容是哪次操作；无备份时也要走完确认才报错。 |
| 证据 | `access_live.go:180-260` 备份文件名含时间戳，但 UI 只暴露「还原最近备份」按钮（`pages/access/access.go:156-159,481-497`）；无列表/时间/大小。 |
| 用户影响 | 改坏后无法回到更早版本；恢复前不知道会回到哪个版本。 |
| 竞品对照 | CC Switch 备份列表/项目；9Router 自动备份。 |
| 类型 | 补状态 + 加功能 |
| 建议处理 | 至少显示「最近备份：MM-DD HH:mm」并在无备份时禁用；随后做备份列表（时间、Agent、文件、大小、触发原因）、选择恢复、恢复前快照、清理策略。 |
| 优先级 | **P1**（与 A0 同批修复语义） |
| 验收 | 无备份按钮禁用；有备份时显示时间；可选择任意备份恢复；恢复前自动快照。 |

### A6：主动健康检查 / 半开探测（P1/P2）

| 项 | 内容 |
|---|---|
| 用户问题 | 渠道冷却到期后，下一个真实请求才再次验证；可能反复撞坏渠道/浪费额度；用户不知道渠道是否恢复。 |

| 优先级 | **P1** |

### A7：通知 / 告警（P1）

| 项 | 内容 |
|---|---|
| 用户问题 | 应用驻留托盘时，全渠道冷却、连续故障转移、额度耗尽不会主动告知；用户只能打开应用才发现。 |

| 竞品对照 | 竞品未完全核实；运维需求明确。 |
| 类型 | 新能力（app/desktop） |
| 建议处理 | 应用内/托盘告警优先；规则：全渠道冷却、连续 N 次切换、额度阈值；去重/限频；可关闭；系统通知用 MyGo 能力，失败降级。 |
| 优先级 | **P1** |
| 验收 | 全渠道冷却触发一次告警；连续切换触发一次；去重/限频；内容不含密钥/prompt；可关闭。 |

| 类型 | 新能力（schema + UI） |

| 优先级 | **P2**（轻量替代 P1） |
| 验收 | 复制渠道保留 base URL/协议/模型建议，可选复制 Key；2 分钟完成主备链；完整池另做 migration 与兼容测试。 |

## 2. B 类：关键体验缺失

> 这些多数不需要新能力，优先修交互/补状态。证据行号来自 UI 子 Agent 审查。

### B1：保存 / 应用 / 备份语义与「待应用」状态

| 项 | 内容 |
|---|---|
| 问题 | 「保存并应用」「仅保存」「应用」「重新应用」「使用中」并存，行为与字面不一致（A0 是最严重的一条）；列表没有「有未应用的修改」状态；「使用中」只是 DB `is_current`，不保证 live 与配置一致。 |
| 证据 | `accesskit/editor.go:85-96`；`access_configs.go:34,37-39`；`access.go:187-189,321-323`；删除 current 后文案「Agent 仍使用其原配置文件」，实际保留 AgentSwitch 写入的受管键（`access_configs.go:131-143`）。 |
| 影响 | 用户不知道当前到底生效的是哪份配置；误判「已保存/已应用」。 |
| 类型 | 现有缺陷 + 纯交互 |
| 处理 | 修交互 + 补状态：保存只落库；应用才投影；列表显示「待应用 / 已应用 / 文件已过期 / 绑定失效」；文案区分「最后应用」与「当前文件状态」。 |
| 优先级 | **P0/P1**（与 A0 同批） |
| 验收 | 编辑 current 后仅保存 → live 不变；列表出现「待应用」；删除 current 后文案准确。 |

### B2：静默部分失败（派生刷新 / 元数据校验）

| 项 | 内容 |
|---|---|
| 问题 | `RegenerateDerived` 失败只记日志，UI 仍显示「已保存/已应用」；Codex 模型元数据非法只在该行报错，不阻止保存，保存后非法值被丢弃。 |
| 证据 | `access_configs.go:94,127,141`；`logicalmodels.go:198-203`；`codex/codex.go:354-398`；`accesskit/editor.go:163-223`。 |
| 影响 | 「配置看起来对、Agent 行为不对」；用户以为已生效。 |
| 类型 | 现有缺陷 |
| 处理 | 补状态：失败摘要返回 UI（区分「已保存、写入失败」）；current 行显示未生效；保存前汇总校验 Codex 元数据并阻止关闭/聚焦错误行。 |
| 优先级 | **P1** |
| 验收 | 注入写失败 → UI 明确失败与路径；非法元数据 → 保存被阻止、文档未变、错误可见。 |

### B3：端口待重启时仍允许应用

| 项 | 内容 |
|---|---|
| 问题 | 改端口后网关仍监听旧端口，但接入编辑器/连接指南使用 `Status.Port`（新端口），仍允许应用，写入 live 指向未监听端口。 |
| 证据 | `bridge/bridge.go:36-49`（Port=配置、Addr=实际）；`access_env.go:15-22`；`guide/guide.go:63-71`；`settings.go:86-95`；`bridge.go:64-73`（重启前不刷新派生）。 |

## 5. 跨页面一致性问题（来自 UI 审查）

1. **成功反馈载体不一致**：全局配置保存/指南复制用 `Toast`，其余用内联 `Feedback`；逻辑模型保存/删除/启停完全无成功消息。用户无法形成稳定预期。
2. **错误位置不一致**：渠道列表在页头下方、接入在列表底部、设置在首卡、Codex 元数据在行下。
3. **主操作位置不一致**：列表页在页头右侧；渠道新建在连接配置卡内部；详情/编辑器在底部。设计系统要求「页头右侧或底部二选一」。
4. **「应用」词汇过载**：「应用」「重新应用」「保存并应用」「仅保存」「使用中」「当前没有配置被应用」同时存在，且行为与字面不一致（A0/B1）。
5. **状态词不一致**：渠道「已停用」vs 逻辑模型「停用」。
6. **反馈语义靠关键词推断**：`InferFeedback` 用中文子串判色；新文案不含关键词就退化成灰色；建议新代码直接传 `FeedbackKind`。
7. **空态不一致**：接入空态没有主操作按钮（只有「点击下方新建配置」），与渠道/逻辑空态不同构。

## 7. 前 5 个最值得先修的问题（不是功能）

1. **A0 保存/应用/备份语义**（P0 缺陷）：它同时破坏「仅保存」的字面承诺和「还原最近备份」的恢复能力；修它不需要新页面，只需把「落库」与「投影」拆开，并把备份放在任何 live 写入之前。
2. **B2 静默部分失败**（P1）：派生刷新失败只进日志、Codex 元数据非法不阻止保存；用户最危险的认知是「已保存/已应用」但实际没有。
3. **B3 端口待重启时的接入写入**（P1）：最容易造成「所有 Agent 同时不可用」的单点；状态真实性是产品核心不变量。
4. **B4 网关状态与冷却重绘**（P1）：侧栏底条是全局唯一状态入口；修复成本低（订阅 `OnState`、过渡态重绘一帧），收益是信任。
5. **B5 删除渠道级联与文案**（P1）：文案说「目标将失效」，实际目标行被永久删除；用户可能在不知情下丢掉故障转移链。

> 紧随其后：B12（首次上手空态与跳转）、B6（绑定失效/模型停用）、B7（备份时间/可用性，建议与 A0 同批）。

## 9. 一句话结论

**页面骨架、视觉 token、滚动、脏检查、异步取消等基础体验已经明显好于旧审计；当前最值得做的不是「再加功能」，而是先让保存/应用/备份的语义与真实写入一致、让失效与部分失败可见，再用持久化历史、端到端验证和用量视图把「可靠」变成可验证的事实。**
