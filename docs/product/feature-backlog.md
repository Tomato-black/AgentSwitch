# AgentSwitch 候选功能池与优先级（2026-10-29）

> 配套：`competitive-analysis.md`、`capability-matrix.md`、`feature-gap-analysis.md`、`roadmap.md`、`decisions.md`。
> 本文不是排期承诺；复杂度为相对量级（S/M/L/XL），依据见每项说明。RICE 分数用于相对排序，不是精确预测。

---

## 1. 目标用户与假设

| 代号 | 用户 | 特征 | 是否当前目标 |
|---|---|---|---|
| S1 | 中文个人开发者 | 使用 Claude Code / Codex / Claude Desktop；2–5 个渠道；关注稳定、隐私、配置简单 | **主目标** |
| S2 | 多供应商/多订阅重度用户 | 多个 Coding Plan/API Key；额度敏感；愿意折腾 | **主目标（高价值）** |
| S3 | 小团队/共享网关 | 多人共用、需要配额/审计/远程访问 | 非当前目标；不为其做架构 |
| S4 | 全球开源用户 | 英文界面、Gemini/Cursor 等更多工具 | 潜在；取决于定位决策 |

关键假设（需后续验证）：
- **H1**：S1/S2 的主要痛点不是「渠道不够多」，而是「故障时不知道为什么、改坏后怎么恢复、钱花在哪」。
- **H2**：S2 对多账号有真实需求，但「渠道复制 + 主备链」可能覆盖多数场景，未必需要完整密钥池。
- **H3**：用量/成本统计有价值，但「账单级准确」不是必需；估算 + 相对比较即可。
- **H4**：零云/本地隐私是差异化，不应为了多机同步引入云账号。

## 2. 评分方法

`RICE = Reach × Impact × Confidence ÷ Effort`

| 因子 | 取值 | 说明 |
|---|---|---|
| Reach | 1–5 | 当前目标用户（S1+S2）中受影响的比例 |
| Impact | 0.25 / 0.5 / 1 / 2 / 3 | 3=核心信任/流程；2=显著效率；1=体验改善；0.5=边缘 |
| Confidence | 0.5 / 0.8 / 0.9 / 1.0 | 无用户证据时不超过 0.8 |
| Effort | 1–5 | 1=1–2 天；2=3–5 天；3=1–2 周；4=2–4 周；5=>1 个月（含架构/schema） |

**注意**：现有缺陷修复（P0-0）不参与 RICE 排序——它不是「可选功能」，而是信任底线，必须先修。

## 4. 最值得开发的五项功能（推荐）

> 前提：先完成 **P0-0 保存/应用/备份语义修复**（缺陷修复，不占五项名额）。以下五项按**推荐顺序**排列，综合战略权重（可信闭环/差异化/首次上手），不完全等同于 §3 的 RICE 排名；用量（A3）因竞品基础能力与订阅用户价值被战略上调。

### 4.1 请求/路由历史持久化与故障解释（P0）

- **用户问题**：故障发生时不知道网关试了哪些目标、为什么跳过、冷却到几点、哪个上游慢；重启后记录清零。
- **目标用户与场景**：S1/S2；上游 429/5xx、切换后仍失败、Agent 报错需要排查。
- **为什么现状解决不好**：`internal/telemetry/ring.go` 只有 100 条内存环；UI 只显示 20 条；无持久化、筛选、导出。
- **竞品证据**：CC Switch 请求日志/用量；CCR 请求/响应详情/trace；LiteLLM 日志/回调；new-api 日志/playground；9Router 请求/翻译日志。
- **预期收益**：把「翻日志猜原因」变成「30 秒内定位」；支撑「可解释故障转移」的核心承诺；降低支持成本。
- **成本与风险**：M–L（schema + 写入路径 + UI + 保留策略）；不能记录 prompt/response 正文；不能阻塞 gateway 热路径；磁盘轮转/保留期。
- **依赖模块**：`internal/telemetry`、`internal/gateway`、`internal/storage`、`internal/bridge`、设置页。
- **数据/接口/架构变更**：是。新增 SQLite 表/迁移；`RequestRecord` 增字段（tokens、channel_id、upstream_status）；bridge 查询/导出；UI 历史视图。
- **如何验证价值**：5 名目标用户完成「模拟 429 排障」，记录找到原因的时间与是否需要打开日志文件；发布前后对比支持问题中「不知道为何失败」的比例。
- **验收**：重启后历史仍在；可按状态/模型/渠道/时间筛选；尝试链含渠道/模型/跳过原因/耗时；导出 JSON/CSV + 脱敏诊断包；不存正文；`-race` 通过。

### 4.2 端到端测试 / 接入验证 Playground（P0）

- **用户问题**：配置完渠道/逻辑模型/接入后，不知道整条链是否真的通；只能打开 Agent 发真实请求。
- **目标用户与场景**：S1 首次接入；S2 调整目标链/换 Key 后验证。
- **为什么现状解决不好**：渠道详情只有「测试连通」，不测逻辑模型/目标链/接入；逻辑模型页无测试入口。
- **竞品证据**：CCR 协议探测/连通性/模型发现；new-api Playground；LiteLLM health；CC Switch 连通性检查（只测可达性）。
- **预期收益**：首次上手闭环；失败时快速区分 Key/模型名/协议/冷却/接入文件问题；降低「配置完不生效」的挫败感。
- **成本与风险**：S–M；测试请求会产生少量费用；需要明确提示；测试不应污染生产冷却/统计（或单独标记）。
- **依赖模块**：`internal/provider`、`internal/gateway`、`internal/bridge`、逻辑模型页/接入页。
- **数据/接口/架构变更**：bridge 新增测试方法；可能复用现有 provider 探测；不需要 schema。
- **如何验证价值**：新用户不读 README 完成首次接入并通过测试请求；失败场景中用户能说出下一步。
- **验收**：选择逻辑模型发测试请求，显示每个目标成功/失败/耗时/命中目标；失败显示下一步；不泄露密钥；有费用提示；Fake Provider 覆盖 401/429/404/全冷却。

### 4.3 备份列表 + 配置导出/导入（P1，与 P0-0 同批设计）

- **用户问题**：只能还原最近一份；不知道备份时间/内容；换机/重装无法带走配置。
- **目标用户与场景**：S1/S2 改坏配置、换机、重装、分享配置。
- **为什么现状解决不好**：备份文件名有时间戳但 UI 只暴露「还原最近备份」；无应用配置导出/导入。
- **竞品证据**：CC Switch 首写/每日备份 + 导入导出 + Deep Link + 云同步；9Router 自动备份；LiteLLM/new-api DB/部署备份。
- **预期收益**：配置成为可迁移资产；用户敢试错；降低迁移/重装流失；为「反锁定」承诺。
- **成本与风险**：M；导出是新的泄露面——默认不含明文密钥，可选密码加密；格式版本化；导入预览/回滚。
- **依赖模块**：`internal/storage`、`internal/bridge`、`internal/credential`、接入页/设置页。
- **数据/接口/架构变更**：是。版本化导出格式；可选加密；备份元数据；导入校验；不破坏现有 schema。
- **如何验证价值**：迁移演练 A→B 后 Claude Code/Codex 各发一条请求成功；用户能在 5 分钟内完成换机；导出文件无明文密钥（自动化扫描）。
- **验收**：备份列表显示时间/Agent/大小/触发原因；可选择恢复；恢复前自动快照；导出/导入含渠道/逻辑模型/接入配置/设置；默认不含密钥；导入前预览差异；冲突可回滚。

### 4.4 用量/成本/配额可见性（P1）

- **用户问题**：不知道本周/本月用了多少 token、哪个渠道最多、额度大概还剩多少；切换目标后成本变化不可见。
- **目标用户与场景**：S2 多订阅/多 Key 用户；按量付费用户；需要判断故障转移是否值得的用户。
- **为什么现状解决不好**：`RequestRecord` 无 token/cost；协议层已解析 usage 但网关未记录；无 usage 表/价格表。
- **竞品证据**：CC Switch usage/heatmap/custom pricing；CCR token/cost/latency；9Router 配额窗口/成本估算；LiteLLM spend tracking；new-api usage logs。
- **预期收益**：回答「钱花在哪、额度还剩多少」；为故障转移/目标链调优提供依据；提升订阅用户留存。
- **成本与风险**：M–L；需从三种协议/流式响应提取 usage；价格表维护；订阅套餐无法精确美元化；估算误差可能引发不信任。
- **依赖模块**：`internal/protocol`（usage 提取）、`internal/gateway`、`internal/telemetry`、`internal/storage`、UI。
- **数据/接口/架构变更**：是。usage 字段/表；价格表（内置 + 用户可编辑）；bridge 查询；UI 聚合视图。
- **如何验证价值**：用 3 家供应商控制台对照 token 误差 <5%；用户 1 分钟内回答「本周哪个渠道消耗最多」；成本标注「估算」。
- **验收**：非流式/流式均提取 token；按渠道/模型/日聚合；成本可编辑且标注估算；可关闭/清理；不承诺账单级准确。

### 4.5 首次上手闭环（动态空态 + 三步清单 + 依赖跳转）（P1）

- **用户问题**：首次上手 12–18 次交互、4 个页面；默认落在逻辑模型页（依赖顺序渠道在前）；空态文案不随数据变化；依赖缺失无跳转。
- **目标用户与场景**：S1 首次安装、空库；新用户不读 README。
- **为什么现状解决不好**：`state.go:363-367` 默认逻辑模型；`logical_view.go:39-47` 固定文案；编辑器依赖缺失只有文案（`accesskit/editor.go:121-123`）。
- **竞品证据**：CC Switch 首次导入/预置/i18n；CCR 桌面引导；9Router dashboard。不是要复制向导，而是让现有页面承担导航。
- **预期收益**：降低首次接入流失；不新增页面/不改 IA；空态即导航。
- **成本与风险**：S；需定义「完成状态」持久化（settings 键）；避免强制 wizard/打断高级用户。
- **依赖模块**：`state`、`shell`、各页空态；P0-2 测试请求可复用。
- **数据/接口/架构变更**：settings 增「onboarding 完成状态」键；无 schema 变更。
- **如何验证价值**：5 名不读 README 的用户完成首次接入；记录完成率/时间/卡点。
- **验收**：空库首屏指向渠道；有渠道无模型时空态改为「新建逻辑模型」；三步清单可见、可点击、完成状态持久化；依赖提示可跳转；不阻塞高级用户。

> **紧随其后（第 6–8 名）**：通知/告警、渠道复制+主备链、搜索/筛选。它们有价值，但应排在上述五项之后。

| 会话阅读/搜索 | 不做 | 隐私敏感；格式复杂 | 不做 |
| Token 压缩/RTK/提示词注入 | 不做 | 改变模型行为；破坏透明网关信任 | 不做；若做必须默认关闭并显著标注 |
| 云同步 | 不做 | 与本地优先/零云冲突 | 用加密导出/导入替代 |
| 多租户/团队/虚拟 Key/计费 | 不做 | 服务端 SaaS 形态 | 团队版立项时另做架构 |
| Guardrails/语义缓存 | 不做 | 非个人开发者核心问题 | 不做 |
| 插件系统 | 不做 | 稳定性/安全冲突 | 不做 |
| OAuth 官方订阅登录 | 暂缓 | 条款/合规/技术复杂 | 用户强烈需求且法务可行 |
| 远程访问/移动端 | 不做 | 破坏 loopback 安全模型 | 不做 |
| CLI/无头模式 | 暂缓 | 与桌面优先定位冲突 | 明确团队/服务器需求 |
| 成本感知路由 / Fusion | 长期 | 需要可靠价格/质量数据 | 先有 A3 用量与用户证据 |

## 7. 依赖关系

```
P0-0 保存/应用/备份语义 ──┬──> A5 备份列表
                          └──> B1 待应用状态

A1 历史/诊断 ──┬──> A3 用量/成本
               ├──> A7 告警
               ├──> B14 搜索/筛选
               ├──> B8 日志打开
               └──> A6 半开探测

A2 端到端测试 ──> B12 首次上手闭环

A4 导出/导入 ──> C3 从 cc-switch 导入
              └──> C1 配置 diff（可独立）

C2 渠道复制 ──> A8 完整密钥池（仅在有证据时）
```

**关键路径**：P0-0（写入一致性）→ A1（历史基础设施）→ A3/A7/B14/A6（基于历史的能力）。不要先做用量/告警再补历史，否则会重复返工。

## 8. 价值验证与淘汰机制

### 8.1 验证原则

- 每个 P0/P1 功能上线前，定义 1 个**用户可感知结果**和 1 个**可测量指标**（本地/自愿反馈，不做暗上报）。
- 优先用 5 名目标用户的任务测试，而不是只看代码完成度。
- 不在没有用户证据时承诺「账单级准确」「团队级配额」「12 工具支持」。

### 8.2 淘汰标准

| 信号 | 处理 |
|---|---|
| 功能上线 4 周内使用率 <5%（本地统计/自愿反馈） | 降级为 P2，停止继续投入 |
| 用户无法在 1 分钟内说出该功能的价值 | 回到问题定义，不做扩展 |
| 维护成本超过每次发布 10% 工作量 | 冻结扩展，评估移除 |
| 与隐私/安全默认冲突 | 立即停止，重新设计 |

### 8.3 待验证假设

- H1：用户更痛的是「不可解释/不可恢复」而非「渠道少」。
- H2：渠道复制 + 主备链能覆盖多数多账号需求。
- H3：估算用量足够，账单级不是必需。
- H4：用户接受「不做云同步，用加密导出/导入替代」。
- H5：首次上手问题可以通过动态空态 + 三步清单解决，不需要向导页。
- H6：用户愿意为「可靠性/可解释性」付出一定的配置复杂度。
